# Operating Guide

이 문서는 현재 작업자의 Claude Code 운영 스타일을 유지하기 위한 일반 운영 가이드다.

## 핵심 원칙

- 한 터미널에는 한 역할만 부여한다.
- 한 터미널은 한 시점에 하나의 작업 문서만 담당한다.
- 다른 기능이나 다른 화면 작업은 새 터미널로 분리한다.
- 작업 상태는 `docs/progress/`, 완료 결과는 `docs/done/`, 큰 방향은 `docs/plan/INDEX.md`에서 관리한다.

## 문서별 책임

- `docs/plan/`: 기능 단위 로드맵과 우선순위 관리
- `docs/progress/`: 현재 세션의 작업 상태 관리
- `docs/done/`: 완료된 작업 결과와 후속 과제 관리

### 판단 기준

- 이 기능이 왜 필요하고 우선순위가 무엇인지 정리하면 `docs/plan/`
- 지금 누가 무엇을 작업 중인지 정리하면 `docs/progress/`
- 결국 무엇이 반영되었는지 정리하면 `docs/done/`

### 중복 방지 원칙

- `docs/plan/`에는 세션 로그를 적지 않는다.
- `docs/progress/`에는 프로젝트 전체 우선순위를 적지 않는다.
- `docs/done/`에는 진행 중 메모를 적지 않는다.
- `docs/plan/`의 완료는 상태 표시만 남기고, 상세 결과는 `docs/done/`에 적는다.

## 역할 사용법

- `역할 기획`: 서비스 방향, 일반 개념 설명, 검증, 질답
- `역할 화면개발`: 화면 수정, 사용자 동작 연결, UI 개선
- `역할 기능개발`: 실제 기능 구현, 프론트-백 연계, GCP/백엔드 포함
- `역할 리팩토링`: 버그 수정, 공통화, 구조 개선

## 추천 운영 방식

### 1. 새 작업이 생겼을 때

- 기존 터미널의 컨텍스트를 유지하고 싶으면 새 터미널을 연다.
- 새 터미널에서 역할 호출을 먼저 한다.
- 해당 작업용 `docs/progress/*.md` 문서를 생성하거나 갱신한다.
- 기능 단위 로드맵 문서가 없으면 `docs/plan/`에 기준 문서를 만든다.

### 2. 작업 중일 때

- 같은 작업 문서 안에서만 상태를 갱신한다.
- 범위 변경, 제외 범위, 다음 액션을 짧게 기록한다.
- 다른 작업이 생겨도 기존 문서에 섞어 쓰지 않는다.

### 3. 작업이 끝났을 때

- 결과를 `docs/done/*.md`로 정리한다.
- `docs/plan/`에는 해당 항목의 상태만 `완료`로 갱신한다.
- 후속 작업이 있으면 `docs/plan/INDEX.md`에 남긴다.

## 예시

### 예시 A. 로그인 기능 구현 + 로그인 화면 수정

- A 터미널: `역할 기능개발`
- 문서: `docs/progress/login-api.md`
- 작업: 로그인 API, 인증 상태, 백엔드 연계

- B 터미널: `역할 화면개발`
- 문서: `docs/progress/login-ui.md`
- 작업: 로그인 폼, 버튼 상태, 에러 메시지, 엔터 제출

이 경우 두 터미널은 같은 사용자 기능군을 다루지만, 작업 문서가 다르므로 컨텍스트가 덜 섞인다.

### 예시 B. 로그인 작업 중 회원관리 화면 수정 요청

- 기존 B 터미널이 `docs/progress/login-ui.md`를 담당 중이라면, 같은 터미널에서 `member-ui`까지 바로 섞지 않는다.
- 새 터미널을 열고 `역할 화면개발`로 시작한다.
- 새 문서 `docs/progress/member-ui.md`를 생성하거나 갱신한다.

이 원칙의 목적은 기존 터미널의 맥락을 보호하는 데 있다.

## 운영 관련 질문

- 운영 방식이 헷갈리면 `역할 기획` 터미널에서 질문한다.
- 이 경우 답변 기준 문서는 `AGENTS.md`, `docs/agent/MULTI_TERMINAL_WORKFLOW.md`, 이 문서다.
